# Huawei Deck 后期可视化微调编辑器设计

- **日期：** 2026-08-01
- **状态：** 已完成交互与架构评审，待书面规格审查
- **试点对象：** `Deck-Projects/renzhi/renzhi-deck.html`
- **推广目标：** 试点稳定后沉淀为 `huawei-deck` skill 的通用后期微调能力

## 1. 背景

`huawei-deck` 当前擅长由 Agent 批量生成、重写和验证单文件 HTML deck，但在制作后期存在两个效率瓶颈：

1. 用户难以在 Agent 对话中准确描述某个页面区域、元素或偏移量；
2. 改文字、拖位置、调大小等局部操作，用户直接手改往往比让 Agent 修改更快。

试点 deck 有 21 页，文件约 30 MB，解码后的 template 约 170 万字符。页面、动画和交互均封装在 bundle 的 template JSON 字符串中，正式写回必须继续遵守 `scripts/edit-bundle.py` 的编码与结构约束。

仓库内已有一份 `renzhi-deckstudio-replica`，但转换结果只有 19 页，且每页主体退化为单个 `freeform`，无法逐项编辑。这说明“先转成另一套场景图，再做编辑”无法满足本项目的无损要求。

## 2. 目标与非目标

### 2.1 目标

- 用户在浏览器中直接修改常见文字、位置和大小；
- 用户可以鼠标拉框圈选任意区域，在选区旁输入修改意见；
- 多条修改意见可以跨页积累，再一次性交给外部 Codex 或 Claude Code 处理；
- 人工修改与 Agent 修改进入同一操作日志，支持单条撤销和整批撤销；
- Agent 修改实时反映到画布，不要求刷新整份 deck；
- 完整保留当前 21 页、放映动画、交互组件和单文件离线能力；
- 保存失败、定位歧义或文件冲突时不破坏原 deck；
- 先在 `renzhi` 上验证，再抽象成 skill 通用能力。

### 2.2 第一版非目标

- 不在编辑器中内置完整聊天系统；
- 不增删页面、不调整页序；
- 不重构复杂 SVG、动画或自定义交互；
- 不把现有 deck 全量转换成结构化场景图；
- 不在第一版提供正式 MCP 包装，先稳定 CLI/HTTP 接口；
- 不替代现有的大改工作流、`edit-bundle.py` 或 verify 三件套。

## 3. 核心方案

采用“**原 deck + 编辑覆盖层 + 本地协作桥 + 可撤销补丁**”方案。

- 原 deck 始终是渲染底座，不做格式转换；
- 编辑器通过同源 iframe 直接加载原 deck；
- 选择框、区域标记、属性面板和任务记录由外层编辑器绘制；
- 所有人工与 Agent 修改先成为结构化动作，作用于实时画布并进入操作日志；
- 编辑会话保存在 sidecar 中；
- 用户明确执行“写回 deck”时，只把最终有效补丁及小型补丁执行器嵌入单文件 bundle；
- 正式写回继续经过 `edit-bundle.py`、临时文件验证和原子替换。

该方案不改写原有动画、SVG 和交互结构，因此比场景图转换更符合无损要求。

## 4. 用户体验设计

### 4.1 启动方式

编辑器提供共享同一编辑服务的桌面与命令双入口。macOS 用户直接双击 skill 根目录的 `Huawei Deck 编辑器.app`，先进入本地网页导入页；点击“添加 Deck HTML”后才唤起系统文件选择器。一次启动只允许成功添加一份 HTML，成功后锁定文件并关闭导入入口，不允许切换；取消选择则可以重试。Skill 生成第一版 deck 并完成基础验证后，也可以把 deck 路径直接传给该应用，绕过导入页直达编辑器。桌面入口只增加一次性导入、首次依赖准备、原生错误提示和浏览器关闭后的服务回收，不另建编辑或写回实现。

原命令式入口完整保留：

```bash
python3 scripts/deck-editor.py Deck-Projects/renzhi/renzhi-deck.html
```

两个入口都只绑定本机回环地址的服务，并自动打开带随机会话令牌的本地 URL。导入页只允许由同源按钮触发系统选择器，不接收浏览器提供的任意路径；编辑器只允许访问本次选择或传入的 deck 与对应会话目录。

### 4.2 工作台布局

采用评审确认的三栏工作台：

- 顶部：选择模式、区域标记模式、直接改文字、撤销、重做、连接状态和写回按钮；
- 左侧：21 页缩略图、当前页、每页未处理标记数量；
- 中间：原 deck 画布与编辑覆盖层；
- 右侧：常规属性面板；
- 右下角：可展开的 Agent 修改记录抽屉。

编辑器不重复实现 Codex/Claude Code 对话框。完整对话留在外部 Agent，编辑器只负责指代、任务、状态和回执。

### 4.3 区域标记主流程

1. 用户切换到“区域标记”模式；
2. 在当前页鼠标拉框，选区坐标统一换算成 1920×1080 画布坐标；
3. 鼠标松开后，输入框紧贴选区弹出；
4. 用户输入修改意见并点击“提交标记”；
5. 标记进入右下角任务抽屉，当前页缩略图的数量徽标加一；
6. 待处理、失败或待确认标记可二次编辑说明，也可经二次确认删除；Agent 批处理期间锁定改删，已完成任务需先撤销；
7. 用户可继续翻页并重复上述操作；
8. 点击某条记录可跳回原页，并重新高亮原区域；
9. 用户点击“交给 Agent 一次处理全部 N 条”；
10. 外部 Agent 逐条读取区域上下文并提交修改动作；
11. 每条任务独立显示等待、处理中、已完成、需要确认或失败状态；
12. 用户可撤销单条任务，也可撤销整个批次。

区域标记的主要价值是表达“这里怎么改”，不要求用户先命中精确 DOM 元素。

### 4.4 直接编辑模式

区域标记之外保留直接编辑工具：

- 双击常见文字进入就地编辑，只放置光标而不自动全选；鼠标自行选择文字，点击别处或 `Cmd/Ctrl+Enter` 提交；
- 拖动常见元素改变位置；
- 拖动控制点改变大小；
- 复杂 SVG、自定义交互和深层组合组件默认作为整体移动或缩放。

为减少对 Flex/Grid 布局的破坏，第一版移动优先记录独立的位移补丁，整体缩放优先记录独立的缩放补丁；不会为了拖动一个元素而把整页改成绝对定位。

### 4.5 Agent 协作区

Agent 区域不是聊天框，包含：

- 当前连接状态；
- 跨页任务数量与状态；
- 每条任务的页码、摘要和定位按钮；
- Agent 动作的前后差异；
- 单条撤销、批量撤销和重新处理入口。

点击一次“交给 Agent”会冻结当前未完成任务 ID 并立即创建批处理。Agent 连接跟随 Deck 持久化：Skill 启动参数、网页手动设置或首批新建返回的任务 ID 都写入 sidecar，App 重开后继续 resume；只有未绑定时才新建专用会话并加载一次 huawei-deck skill。外部 Agent 仍通过本地协作桥读取任务和提交动作。Agent runner 采用 provider adapter；Codex 为首个实现，Claude Code、OpenCode、OpenClaw 或以后增加的 MCP 只包装同一套底层接口，不改变编辑器数据模型。

## 5. 系统架构

### 5.1 组件

| 组件 | 职责 |
| --- | --- |
| 启动器 | 校验 deck 路径、创建会话、启动本地服务并打开浏览器 |
| 编辑器外壳 | 顶栏、缩略图、属性面板、任务抽屉和快捷键 |
| 原 deck iframe | 同源加载并运行原始 bundle，不转换页面结构 |
| 编辑覆盖层 | 坐标换算、拉框、元素命中、高亮、拖拽和缩放 |
| 会话存储 | 持久化任务、截图、动作、撤销组、基线诊断和 deck 指纹 |
| 本地协作桥 | 提供 CLI/HTTP 读写接口，通过 WebSocket 推送实时更新 |
| Agent 调度器 | 冻结批次、恢复来源会话或创建新会话，并经 provider adapter 推送运行状态 |
| 动作与补丁引擎 | 校验动作、应用预览、合并最终补丁、生成逆操作 |
| 保存适配器 | 调用 `edit-bundle.py`，执行备份、临时写入、验证和原子替换 |
| 诊断适配器 | 运行实时几何检查、`measure_overflow`、截图和动画逐拍验证 |

### 5.2 数据流

```text
用户拉框 / 直接编辑
        ↓
编辑器会话与操作日志
        ↓ WebSocket
本地协作桥 ← CLI / HTTP → 外部 Codex / Claude Code
        ↓
结构化动作 → 实时画布 → 撤销日志
        ↓ 用户明确“写回 deck”
补丁合并 → edit-bundle.py → 临时文件验证 → 原子替换
```

### 5.3 并发规则

- 编辑器会话拥有递增的 `revision`；
- Agent 提交动作时必须携带其读取任务时的 revision；
- revision 已变化时返回冲突，不把旧动作静默覆盖到新画布；
- 编辑器打开期间，外部工具不得直接修改同一 deck；
- 文件监视发现 deck 指纹变化后立即暂停正式写回。

## 6. 数据模型

### 6.1 页面身份

当前 deck 存在三个同名“目录页”，因此不能把 `data-label` 当作唯一键。

每页使用稳定 `pageKey`，由会话启动时的页面序号、标签和页面结构指纹共同确定。任务同时保存显示用页码和标签。若外部文件变化导致页面指纹不再匹配，任务进入“需要重新定位”，不得仅凭同名标签猜测。

### 6.2 区域任务

```json
{
  "id": "task-0004",
  "pageKey": "page-009-8f21c4a1",
  "pageIndex": 9,
  "pageLabel": "kc-sol-agent",
  "rect": { "x": 112, "y": 196, "w": 760, "h": 420 },
  "instruction": "三张小卡再大一点，减少上面的空白",
  "snapshotPath": "snapshots/task-0004.png",
  "candidates": ["locator-a", "locator-b"],
  "status": "pending",
  "createdAt": "2026-08-01T21:00:00Z"
}
```

区域任务保存：页面身份、标准画布坐标、用户意见、局部截图和按相交面积排序的候选元素。候选元素只为 Agent 提供线索，不自动等同于最终修改目标。

### 6.3 元素定位器

元素定位器包含：

- `pageKey`；
- 渲染 DOM 相对路径；
- 标签名；
- 初始文本、类名和关键样式指纹；
- 原始几何框。

运行时按这些信息生成确定性编辑 ID。路径命中但指纹差异过大，或多个候选同样匹配时，操作进入“需要确认”。新补丁不会依赖不稳定的屏幕像素或单独一段文本。

### 6.4 修改动作

第一版受控动作包括：

- `setText`：修改纯文本；
- `setStyle`：修改白名单内的样式属性；
- `translate`：记录相对位移；
- `resize`：记录宽高或整体缩放；
- `hide` / `show`：隐藏或恢复目标。

每个动作记录任务 ID、目标定位器、动作类型、修改前值、修改后值和 revision。人工直接编辑与 Agent 修改使用同一动作格式。

第一版不接受任意脚本、内联事件处理器、外部 URL 或未经约束的整页 HTML 替换。

## 7. 会话、补丁与保存

### 7.1 Sidecar

编辑会话保存在 deck 所在项目的隐藏目录：

```text
.huawei-deck-editor/
  renzhi-deck-8f21c4a1/
    session.json
    snapshots/
    backups/
```

目录名末尾的八位字符串取自 deck 指纹。sidecar 保存：区域任务、局部截图、动作历史、撤销组、连接状态、基线诊断和备份。它不进入最终交付 deck，并应加入项目忽略规则。

### 7.2 最终补丁

“写回 deck”前，动作引擎按目标和属性合并操作：

- 多次修改同一文本只保留最终值；
- 连续位移合并为最终位移；
- 已被撤销的动作不进入补丁；
- 任务说明、局部截图和历史回执不进入补丁。

最终 bundle 只新增：

1. 压缩后的有效补丁数据；
2. 一个小型离线补丁执行器。

补丁执行器等待原 deck 挂载完成，为目标计算确定性编辑 ID，并按顺序应用补丁。若原 React 运行时重建相关 DOM，执行器通过受限观察器重新应用对应补丁。最终 deck 不展示任何编辑 UI。

### 7.3 两种保存

- **保存会话：** 自动执行，只更新 sidecar，不触碰正式 deck；
- **写回 deck：** 用户明确触发，通过保存闸门后才更新正式 HTML。

### 7.4 保存闸门

正式写回必须同时满足：

1. bundle 结构验证通过；
2. 相比会话启动基线，没有新增页面或内层溢出；
3. 磁盘 deck 指纹与会话基线一致。

写回顺序：

1. 在 sidecar 的 `backups/` 中保存原文件备份；
2. 用 `edit-bundle.py` 解码 template；
3. 插入或更新补丁数据与执行器；
4. 经 `set_template` 重新编码；
5. 写入同目录临时文件；
6. 对临时文件执行 `eb.verify` 和保存闸门检查；
7. 全部通过后原子替换正式 deck；
8. 任一步失败均删除临时结果，原文件保持不变。

## 8. 本地协作桥接口

第一版同时提供 CLI 与本机 HTTP 接口，二者调用同一服务层。

最小能力：

- 读取会话概览、当前页、当前选区和 revision；
- 列出跨页任务；
- 获取单条任务的局部截图、区域坐标和候选元素；
- 将任务标记为处理中、需要确认、已完成或失败；
- 提交一组结构化修改动作；
- 撤销单条任务或整个批次；
- 获取修改后的页面截图与实时诊断；
- 触发保存会话和请求正式写回。

服务只绑定回环地址，要求随机会话令牌，不允许跨 origin 调用，也不接受超出启动 deck 与 sidecar 目录的任意文件路径。

## 9. 异常处理

### 9.1 区域指代不清

区域同时命中多个层级、Agent 无法唯一判断目标时：

- 任务状态改为“需要确认”；
- 不自动应用修改；
- 用户可在画布中轮流高亮候选；
- 用户可缩小区域或补充说明后重试。

### 9.2 修改造成新溢出

- 每次任务完成后对修改页执行实时几何诊断；
- 与会话启动时的已知基线比较，只把新增问题视为阻断项；
- 会话与其他标记仍可继续；
- 修复或撤销前禁止正式写回。

### 9.3 Agent 或服务断连

- 用户仍可拉框、写标记和直接手改；
- 任务持续写入 sidecar；
- 批量交给 Agent 的入口暂停；
- 重连后从未完成任务继续，不重复已完成动作。

### 9.4 外部文件变化

- 文件指纹变化后立即暂停正式写回；
- 用户可重新加载新文件，并在新基线上重放补丁；
- 无法重新定位的补丁进入“需要确认”；
- 用户也可选择另存为副本；
- 不提供静默覆盖。

### 9.5 验证或写回失败

- 原文件保持不变；
- 临时文件与错误日志保留到会话目录供诊断；
- UI 显示具体失败阶段和恢复动作；
- 用户可修复后重试或导出当前会话。

## 10. 测试策略

实现采用测试驱动开发，按以下层次验证。

### 10.1 单元测试

- 屏幕坐标与 1920×1080 画布坐标双向换算；
- 页面身份和元素定位器的确定性；
- 区域与元素相交排序；
- revision 冲突；
- 动作校验、合并和逆操作；
- 单条撤销与批量撤销；
- sidecar 持久化和恢复；
- deck 指纹变化检测；
- 补丁编译与幂等应用。

### 10.2 集成测试

以 `renzhi-deck.html` 的工作副本验证：

- 21 页全部挂载；
- 跨至少 3 页连续添加至少 5 条任务；
- 关闭并重新启动编辑器后任务完整恢复；
- 外部 CLI 能读取任务上下文；
- Agent 提交 `setText`、`translate`、`resize` 后画布实时更新；
- 人工直接修改与 Agent 修改进入同一撤销日志；
- 单条撤销、整批撤销和重做均正确；
- 写回后重新打开 deck，修改仍存在；
- 编辑 UI、任务记录和局部截图不出现在最终 deck。

### 10.3 回归与故障测试

- `eb.verify` 验证 bundle 结构；
- `measure_overflow.mjs --all` 比较会话前后溢出；
- `shot.mjs` 检查修改页；
- `steps.mjs` 检查所有被修改的动画页；
- 未修改页面做截图回归，确认补丁未产生旁路影响；
- 进入放映模式，验证翻页、逐拍和现有交互；
- 模拟 Agent 断连、服务重启、revision 冲突、源文件外部变化和损坏补丁；
- 所有写回失败场景均校验原文件哈希不变。

## 11. 验收标准

第一版在 `renzhi` 试点上满足以下条件才视为可推广：

1. 21 页全部加载，现有动画、交互和离线单文件能力保持不变；
2. 用户能完成跨页区域标记、就地输入、批量提交和定位回看；
3. 直接改文字、移动、缩放可用；
4. 外部 Codex/Claude Code 能读取任务并实时提交三类基本修改；
5. 人工与 Agent 修改共享同一撤销日志；
6. 关闭重开后 sidecar 会话正确恢复；
7. 所有歧义、断连、冲突和验证失败都有明确恢复路径；
8. 正式写回通过结构、溢出和文件指纹三重闸门；
9. 保存失败时原 deck 哈希不变；
10. verify 三件套与截图回归通过后，才进入 skill 通用化阶段。

## 12. 推广策略

先只支持 `renzhi-deck.html` 的工作副本，验证真实后期制作流程。试点稳定后再抽象：

- 将 deck 加载、页面发现和坐标换算从试点代码中拆出；
- 在授课、技术分享和工作汇报三套模板上做兼容测试；
- 把启动命令、操作手册和验证流程写入 `huawei-deck` skill 文档；
- 在底层 CLI/HTTP 接口稳定后，再决定是否提供 MCP 包装。

推广阶段仍坚持“原 deck 是渲染底座”，不会改走全量场景图转换路线。
