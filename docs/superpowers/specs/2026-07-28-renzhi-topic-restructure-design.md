# 认知答辩 Deck 双专题重构设计

## 1. 目标

在不削弱现有项目证据的前提下，将专业能力部分从“按能力项逐页罗列”重构为两条专题主线，并强化技术深度：

1. **IT 作战平台构建与新作业模式孵化**：将中路智能体、下路智能体、X+ 与 OCC 远近协同统一为一个专题。
2. **模型训练课题组孵化与赋能**：将训练课题组建设、训战成果、A3 算力估算和产品知识深度统一为一个专题。

同时完成以下内容调整：

- 新增一页“训战产出”。
- 新增一页“AI Coding in Infra & Agent Development”，放入第三章“反思与建议”。
- 重做 A3 算力估算页，体现模型结构理解、剪层、削减专家和单机代理模型估算。
- 重做原 P13 技术管理页，删除开发计划和人员成长地图，突出具体技术贡献。

## 2. 设计原则

- Deck 正文继续使用英文，规格与实现注释使用中文。
- 评委重点关注技术水平，因此技术证据优先于过程描述和人员管理细节。
- 所有未经全量环境验证的算力结果必须表述为“工程估算”，不得宣称完成盲测或精度校正。
- A5 页面不写未经确认的具体硬件参数，只讨论可公开、可解释的架构变化维度及其对训练 Infra 的影响。
- 保持现有华为红品牌视觉语言，品牌红仅用于标题、关键结论和风险强调。
- 不新增自动播放动画；新增页面采用讲者手动推进的 `build` 动画。

## 4. 专题一：IT 作战平台构建与新作业模式孵化

### 4.1 P6 专业能力总览

将现有专业能力总览改成两条主线：

- IT Operations Platform & New Delivery Model
- Model Training Taskforce Incubation & Enablement

每条主线给出“架构设计—技术攻关—规模验证—能力沉淀”的统一阅读框架，帮助评委理解后续页面不是离散项目。

### 4.2 P7 IT 作战平台与新作业模式总体产出

将中路智能体、下路智能体、X+ 与 OCC 放在同一张专题总览中。

页面采用“平台构建 + 作战模式 + 规模结果”三层结构：

- 平台构建：模型迁移调优 Agent、集群集成 Agent、知识与工具底座。
- 作战模式：现场 FAE、OCC 作战中心、远程专家和 Agent 平台协同。
- 规模结果：优先采用材料中已有的项目数、需求数、闭环率、知识资产和月活数据；每个数字需能追溯到项目材料。

### 4.3 P8–P10 技术证据

- P8 展示作战平台的分层架构、数据闭环和远近协同关系。
- P9 用 CAD → 3D 数字孪生证明下路智能体的结构化识别与工程落地能力。
- P10 用 CTC Loss 跨 PTA / aclnn / AICPU 的内存踩踏问题证明 X1+ 现场跨层定位能力。

### 4.4 P11 技术问题解决与技术治理

删除原页面中的开发计划、双轨时间轴和人员成长地图。

页面左侧约三分之二展示三个具体技术问题：

1. **性能基线检索不准**
   - 非标准输入解析。
   - 模型名、量化方式和卡数规范化。
   - 多维 SQL 取交集。
   - Reranker 语义重排。

2. **Agent 业务流程不稳定**
   - 区分“固定靶”与“移动靶”。
   - 使用 Workflow 保证关键流程方向。
   - 使用 Agentic Workflow 承担检索、分析和工具调用。

3. **Skills 与知识协同不足**
   - 稳定流程沉淀为 Skill。
   - 高频变化信息进入知识库。
   - 结合执行轨迹、BadCase 和用户反馈持续修正。

页面右侧约三分之一保留技术治理：

- 技术目标拆解为责任人、验收证据和发布门禁。
- 关键路径资源冲突时冻结非关键功能。
- 后端、MCP、前端、安全与 HIS 联合验证。
- 使用一个已闭环风险案例说明管理如何服务技术交付。

## 5. 专题二：模型训练课题组孵化与赋能

### 5.2 P14 训战产出

页面采用左右双栏。

左侧约 45%：A5 架构变化对训练 Infra 的影响。只使用四类变化维度：

1. 计算与拓扑：影响 TP / PP / EP / DP 的映射与整机粒度。
2. 内存层级：影响参数、激活、优化器状态的驻留、重计算与 Offload。
3. 通信路径：影响集合通信、计算通信重叠和长稳训练。
4. 软件栈与算子：影响 Megatron、MindSpeed、VeRL、CANN 算子及版本适配。

右侧约 55%：训战成果时间轴与产品知识深度。

- X1+：SFT / DPO、训推融合特性验证、现场训练与推理问题闭环。
- 训练课题组：Qwen2.5-7B GRPO、AIME / MATH 指标提升、8 项加速特性验证。
- A3 / A5：从模型结构、并行策略、显存和通信约束出发进行训练资源设计。
- 能力赋能：课程覆盖 2,000+ 人、培养 8+ 讲师、满意度 98%+。

底部用四层技术栈表达产品知识深度：

`模型结构与算法 → 训练框架 → 并行与资源 → CANN / HCCL / 算子`

### 5.3 P15 A3 结构驱动的算力工程估算

页面用“结构理解—代理模型—实测外推—结果边界”讲述。

#### 模型结构理解

- 总参数量决定权重驻留与显存下限。
- 激活参数量决定单 Token 计算量。
- 层数决定重复计算深度。
- Top-K、专家分布与 EP 决定路由与通信开销。

#### 单机代理模型

- 保留隐藏维度、注意力头、MoE Block、Top-K 和数据类型。
- 剪层以降低重复计算深度。
- 削减专家总数以降低权重驻留，使模型能够在单台设备运行。
- 明确注明代理模型只用于提取计算与显存量级，不等同于完整模型。

#### 实测与外推

测量代理模型的 Attention、MoE、显存峰值和关键训练阶段耗时，再结合完整模型的层数、专家总数、并行策略和拓扑约束进行解析外推。

#### 结果边界

- 输出下界、建议值和风险上界，不输出伪精确的单一数字。
- 当前没有全量环境进行盲测与误差校正。
- 跨机 EP 通信、负载不均衡和 P95 长尾主要依赖解析估算。
- 结果用于资源规划与方案比较，最终需在目标环境校准。

## 6. 第三章：AI Coding 与开放反思

### 6.1 P18 AI Coding in Infra & Agent Development

页面采用“实践—边界—思考”三段式。

#### 实践

- Infra：辅助阅读 VeRL、Ray、Megatron、MindSpeed 调用链，生成调测脚本与日志打点，处理版本兼容和源码级适配，自动化分布式训练环境部署与测试。
- Agent：将交付流程封装为 Skills / MCP，辅助构建 RAG、评测与 BadCase 闭环，快速开发 AICO-PPT、AICO-Bot、分布式训练工具和文档抽取工具。

#### 边界

- 适合：代码理解、重复性改造、测试生成、日志分析、工具编排和快速原型。
- 不适合直接放权：模型结构与并行策略决策、性能结论、生产变更、跨组件根因判定。
- 所有结论必须经过代码、日志、测试或目标环境验证。

#### 思考

核心观点：

> AI Coding 的价值不是替代工程判断，而是把“理解系统—修改代码—验证结果—沉淀能力”的闭环速度放大。

开放问题：

> 当代码生成越来越便宜，工程师真正稀缺的能力将转向系统理解、问题定义、验证设计和结果负责。

### 6.2 P19–P20 递进关系

- P18 从具体 AI Coding 实践进入开放问题。
- P19 将讨论上升到人机协同、数据与评测、Agent 化作业和 FAE 能力演进。
- P20 回到个人待改进项，形成“技术实践—行业反思—个人成长”的收束。
